# S6-03 — encrypt the token store at rest (reversible-pseudonymization token vault)

> **Cold-pickup invariant**: executable cold. This story hardens the reversible-pseudonymization token vault so the de-tokenization mapping (`scope → token → plaintext`) is **never persisted unencrypted**. The on-disk transform is **authenticated encryption (AEAD)** of each plaintext value (+ envelope-wrapped data key + integrity tag verified on read, **FAIL LOUD on tamper**). The AEAD math + round-trip + tamper-detection are **pure-Python over the `cryptography` AEAD primitive already in the `[crypto]` extra** (`AESGCM`/`ChaCha20Poly1305` — verified importable; no new dependency) → fully testable in-tree with a synthetic test key + synthetic PII. Real KMS / real key custody (HSM, cloud KMS) is the **Pass-2 / AGENT_SIMULATED honesty boundary** (an in-tree test KEK stands in for the custodian). **Additive only**: a new `EncryptedSQLiteTokenStore` implementing the existing `TokenStore` ABC — the plaintext-leaking `SQLiteTokenStore` and `providers.py`/`reidentification.py`/`key_manager.py` stay byte-identical.

## 1. Intent
Close **SME Security MAJOR #2**: the reversible-pseudonymization vault (`SQLiteTokenStore`, `src/pii_anon/tokenization/store.py`) writes the original PII to disk **in cleartext** — column `plaintext TEXT NOT NULL` (`store.py:194`) populated by a bare `INSERT OR REPLACE … VALUES (?, … mapping.plaintext, …)` (`store.py:239–257`), and read straight back at `get`/`list_by_scope` (`store.py:259–310`). Anyone with the `.db` file recovers every original value — a direct violation of **FR-026 / AX-006** (no raw PII persisted post-masking) and a confidentiality hole under **NFR-014** (unauthorized-reversal must = 0). 

Ship an **additive** `EncryptedSQLiteTokenStore` that implements the same `TokenStore` interface but persists every sensitive field (`plaintext`, and — defense-in-depth — `token`/`scope`/`entity_type`) under **authenticated encryption (AEAD)**: a per-row ciphertext + nonce + auth tag, with the data-encryption key (DEK) itself **envelope-wrapped** by a key-encryption key (KEK) the store never persists in the clear. On read, the AEAD tag is **verified**; a tampered ciphertext (or tampered associated data) makes decryption **raise loudly** (`TokenStoreIntegrityError`) — never silently return wrong/partial plaintext. The KEK is supplied by a pluggable **`EnvelopeKeyProvider`** seam (key-id + rotation): the in-tree `StaticTestKeyProvider` is AGENT_SIMULATED; a real custodian (cloud KMS / HSM / OS keyring) drops in behind the same protocol at Pass-2. Deterministic pseudonymization (**AX-002**) and anon-vs-pseudo separation (**AX-004**) must still hold end-to-end after the store is swapped in.

## 2. Approach / scope
- **`EncryptedSQLiteTokenStore(TokenStore)`** (new, in `encrypted_store.py`) — subclass of the abstract `TokenStore` (so it is a drop-in wherever `TokenStore` is typed, incl. the orchestrator's `token_store: TokenStore | None` seam, **without touching orchestrator.py**). Same public surface: `put`, `get`, `list_by_scope`, `count`, `delete_expired`, `close`. Backed by a SQLite table whose value columns are **opaque ciphertext blobs**, not text.
- **AEAD per row.** Use `cryptography.hazmat.primitives.ciphers.aead.AESGCM` (default) with `ChaCha20Poly1305` as a constructor-selectable alternative (both verified importable in `.venv`). For each row: generate a fresh 96-bit nonce, encrypt the JSON-serialized sensitive payload, store `(nonce ‖ ciphertext ‖ tag)`. Bind row context as **AEAD associated data (AAD)** — `key_id ‖ scope ‖ token ‖ version` (or a deterministic lookup digest) — so a row's ciphertext cannot be relocated to a different `(scope, token)` slot without the tag failing (thwarts cut-and-paste / row-swap tampering).
- **Lookup vs confidentiality.** The plaintext PII is AEAD-protected and is NOT a query key. To support `get(token, scope=…)` without decrypting every row, persist a **keyed, non-reversible lookup index**: `HMAC-SHA256(index_key, scope ‖ token)` as the row's blind index (the index key is derived from the same KEK material, distinct from the AEAD DEK). This keeps `O(1)` lookup while never storing `token`/`scope` in the clear. (Document the residual: blind-index equality leaks "same (scope,token)" — acceptable; it is a derived pseudonym, not PII, and FR-019 surrogates are deterministic by design.)
- **Envelope / wrapped-key + rotation (the key-management seam).** A `KeyEnvelope` record (stored in a small `_keys` table or sidecar): `{key_id, wrapped_dek, created_at}` where `wrapped_dek = AEAD_KEK(dek)`. The KEK comes from an **`EnvelopeKeyProvider`** protocol — `unwrap(key_id, wrapped_dek) -> bytes`, `current_key_id() -> str`, `wrap(dek) -> (key_id, wrapped_bytes)`. In-tree `StaticTestKeyProvider(test_kek: bytes)` (AGENT_SIMULATED). **Rotation:** a new `key_id` wraps a new DEK; existing rows carry their `key_id`, so old rows still decrypt under the old DEK (mirrors `KeyManager`'s dual-version grace pattern at `key_manager.py:82–114`) — `rewrap_all(new_provider)` re-encrypts under the new key. The KEK / DEK plaintext is **never written to the SQLite file** (NFR-015: artifact-alone re-join FAILs without the external secret).
- **Fail-loud on tamper.** `cryptography` raises `InvalidTag` when the AEAD tag fails. Catch it and re-raise as `TokenStoreIntegrityError` (new subclass of the existing `TokenizationError` in `errors.py`) with the offending `key_id`/blind-index named — never swallow, never return `None`, never return undecrypted bytes.
- **Additive wiring.** Export `EncryptedSQLiteTokenStore`, `EnvelopeKeyProvider`, `StaticTestKeyProvider`, `KeyEnvelope`, `TokenStoreIntegrityError` from `tokenization/__init__.py` (append to `__all__`; do not reorder/remove). Optionally surfaced via `pii_anon.__init__` re-export **only additively** if trivial — otherwise leave `pii_anon/__init__.py` byte-identical and let callers import from the subpackage (see RISK-2).
- **Graceful optional-dep degradation (NFR-026 pattern).** If `cryptography` is absent, constructing `EncryptedSQLiteTokenStore` raises a loud `TokenizationError` with the `pip install pii-anon[crypto]` hint (mirrors the existing `AESSIVTokenizer` guard at `providers.py:112–119`) — module import stays safe so discovery never breaks.

## 2a. Pre-claim de-risk (verified against live code 2026-06-01)
- **RISK-1 (`SQLiteTokenStore` is OFF-LIMITS / public API):** `SQLiteTokenStore` is re-exported from `pii_anon.__init__` (`__init__.py:103,211`) and consumed by `orchestrator.py` (user-WIP, OFF-LIMITS). Do **not** modify `store.py` to encrypt in place (would change `SQLiteTokenStore`'s on-disk format = public-API/behaviour regression + orchestrator coupling). The fix is a **new sibling class**; `store.py` stays byte-identical. The orchestrator already accepts any `TokenStore` (`orchestrator.py:198 self.token_store = token_store or InMemoryTokenStore()`), so the encrypted store is opt-in by passing it in — **no orchestrator edit needed**.
- **RISK-2 (`pii_anon/__init__.py` edit risk):** prefer the narrow path — export only from `tokenization/__init__.py`. If a top-level re-export is added it must be **append-only** to the existing `__all__` block (`__init__.py:208–211`) and md5-diffable as additive; if any doubt, leave `pii_anon/__init__.py` byte-identical (the class is fully reachable via `from pii_anon.tokenization import EncryptedSQLiteTokenStore`).
- **RISK-3 (no new dependency):** `AESGCM`/`ChaCha20Poly1305` import-verified from `cryptography.hazmat.primitives.ciphers.aead`; `cryptography>=41.0` is already the `[crypto]` extra (`pyproject.toml:110`). Use the **same** import path the codebase already uses for `AESSIV` (`providers.py:11–14`). Add **no** new package; do **not** introduce an unsafe-deserialization path (no unsafe-deserialization-style loaders) for the on-disk payload — serialize with `json` over a small explicit field dict (the payload is decrypted bytes → `json.loads`, never an arbitrary-object loader).
- **RISK-4 (no shell-out / no subprocess):** key material is obtained via the in-process `EnvelopeKeyProvider` protocol only; the in-tree provider takes bytes directly. Do **NOT** shell-out to an external key tool or spawn a subprocess to fetch keys in this story (real KMS clients are Pass-2 and would be a *library* call there, never a shell invocation). The store performs no process-spawning of any kind.
- **RISK-5 (determinism, AX-002):** AEAD nonces are random ⇒ ciphertext is non-deterministic *by design*, but the **pseudonymization tokens are produced upstream by `DeterministicHMACTokenizer`** (`providers.py:49–85`) and are unchanged — the store only persists/returns them. The deterministic-surrogate property (AX-002 / NFR-005) is a property of the tokenizer + key, NOT the at-rest encoding, so a round-trip through the encrypted store returns the identical `TokenMapping` and the same input still yields the same token. Pin this explicitly (acceptance §3).
- **RISK-6 (AX-001 fixtures):** all test PII is **synthetic** (e.g. `"Jane Roe"`, `"jane.roe@example.test"`, `"555-0100"`) — never real. The whole point of the story is that even these synthetic values are unrecoverable from the raw `.db`; the not-plaintext-on-disk assertion scans the file bytes for the synthetic token substring and asserts ABSENCE.

## 3. Given/When/Then (acceptance — concrete, testable, each tagged)
- **A1 — Round-trip preserves the mapping (FR-019, NFR-014). `[UNIT-TEST]`** **Given** an `EncryptedSQLiteTokenStore` backed by a temp `.db` and a `StaticTestKeyProvider(synthetic_kek)`, **when** I `put(TokenMapping(scope="s", token="<EMAIL:v1:tok_abc>", plaintext="jane.roe@example.test", entity_type="EMAIL_ADDRESS", version=1))` then `get("<EMAIL:v1:tok_abc>", scope="s")`, **then** the returned `TokenMapping` equals the input field-for-field (scope/token/plaintext/entity_type/version), and `count()==1`, and `list_by_scope("s")` returns it. TTL/`expires_at` and `delete_expired()` behave identically to `SQLiteTokenStore` (a parametrized contract test runs the SAME assertions against both stores).
- **A2 — On-disk bytes are NOT plaintext (FR-026 / AX-006 — the headline). `[SECURITY-TEST]`** **Given** the store after A1's `put`, **when** I `close()` and read the raw `.db` file bytes (and separately dump every column of every row via a plain `sqlite3` connection), **then** the synthetic plaintext `b"jane.roe@example.test"` does **not** appear anywhere in the file, **and** the plaintext token string `b"<EMAIL:v1:tok_abc>"` does not appear, **and** the value columns are `BLOB` ciphertext (not `TEXT`). A companion assertion: the KEK / DEK plaintext bytes do not appear in the file (NFR-015 — external secret required to reverse).
- **A3 — Tamper a ciphertext byte ⇒ decrypt RAISES (NFR-014, integrity). `[SECURITY-TEST]`** **Given** a populated store, **when** I flip a single byte inside a row's ciphertext blob (via a direct `sqlite3` `UPDATE`) and then `get(...)` that row, **then** it raises `TokenStoreIntegrityError` (subclass of `TokenizationError`) naming the affected row — it does **not** return `None`, the original plaintext, or corrupted bytes. **Property test (`@given`)**: for a synthetic corpus of N mappings, flipping any single byte of any ciphertext/nonce/tag, OR moving a row's blob to a different `(scope, token)` slot (AAD mismatch), ALWAYS raises and NEVER yields a successful-but-wrong decrypt.
- **A4 — Wrong key cannot reverse (NFR-014 / NFR-015). `[SECURITY-TEST]`** **Given** a store written under `StaticTestKeyProvider(kek_A)`, **when** I reopen the same `.db` under `StaticTestKeyProvider(kek_B)` (`kek_B != kek_A`) and `get(...)`, **then** it raises (envelope unwrap / AEAD tag failure) — the artifact alone, or with the wrong external secret, cannot re-join (NFR-015 "artifact-alone re-join = FAIL flagged").
- **A5 — Envelope wrap + key rotation (FR-019 auditable key rotation; DC-04). `[UNIT-TEST]` `[AUDIT]`** **Given** rows written under `key_id="k1"`, **when** I rotate to a new `key_id="k2"` (new wrapped DEK) and `put` new rows, **then** old rows still `get` correctly (decrypt under their stamped `key_id`) AND new rows decrypt under `k2`; **and** `rewrap_all(provider_k2)` re-encrypts the legacy rows so they then carry `k2`; **and** the on-disk `_keys` envelope stores only `wrapped_dek` (never the bare DEK — asserted by scanning the envelope blob for the raw DEK bytes' absence). The set of `key_id`s in use is enumerable for audit.
- **A6 — Deterministic pseudonymization still holds end-to-end (AX-002 / NFR-005). `[CONTRACT-TEST]`** **Given** a `DeterministicHMACTokenizer` + the encrypted store, **when** I tokenize the same `(scope, version, entity_type, plaintext, key)` twice (persisting through the encrypted store) and detokenize via the store, **then** both calls yield the **identical token** and detokenize back to the identical plaintext — i.e. swapping in the encrypted store does not perturb determinism (the token is the tokenizer's HMAC output, independent of the random AEAD nonce).
- **A7 — Anon vs pseudo separation preserved (AX-004 / FR-010). `[CONTRACT-TEST]`** **Given** the encrypted store is a *pseudonymization* (reversible) component, **then** a guard test asserts it exposes only the reversible-mapping surface (`put`/`get`/`detokenize` path) and has **no** code path that emits an anonymization (irreversible) score or merges into an anon family — the encrypted store imports nothing from the anon/eval scoring packages; round-tripping never produces an anon artifact. (Encryption-at-rest is orthogonal to the anon≠pseudo wall and must not breach it.)
- **A8 — Fail-loud on missing crypto dep (NFR-026 pattern). `[UNIT-TEST]`** **Given** `cryptography` is monkeypatched absent (the AEAD symbol is `None`, mirroring `providers.py:13`), **when** I construct `EncryptedSQLiteTokenStore`, **then** it raises a loud `TokenizationError` with the `pip install pii-anon[crypto]` remediation hint — module **import** still succeeds (discovery unaffected).
- **A9 — `TokenStore` Liskov contract (CONTRACT). `[CONTRACT-TEST]`** **Given** the abstract `TokenStore` interface, **then** `EncryptedSQLiteTokenStore` satisfies it (`isinstance(store, TokenStore)` is `True`; all five abstract methods overridden; `get` returns `None` for an absent token — the *absent* case, distinct from the *tampered* case which RAISES). A parametrized suite runs the existing `SQLiteTokenStore` behavioural assertions (scope filtering, TTL expiry, scope-less `get` scan, `count` filters) against the encrypted store and they pass identically.

## 5. Notes / non-goals
- **Non-goal:** real external key custody — cloud KMS, HSM, OS keyring, or any networked secret manager — is **Pass-2 / AGENT_SIMULATED-now**. The `EnvelopeKeyProvider` protocol is the seam; the in-tree `StaticTestKeyProvider` stands in. Mark honestly in Evidence; do not claim real-KMS behaviour.
- **Non-goal:** migrating existing `SQLiteTokenStore` `.db` files to the encrypted format (a one-shot migration utility is a follow-up). `SQLiteTokenStore` stays as-is for the in-memory/short-lived path; the encrypted store is the at-rest-persistence recommendation.
- **Non-goal:** changing the tokenizer or `KeyManager` (`providers.py` / `key_manager.py` byte-identical). This story encrypts the **store**, not the surrogate algorithm; the two key concepts are deliberately distinct (tokenizer key = surrogate determinism; store KEK = at-rest confidentiality).
- **Non-goal:** the full S6-03 *session-pseudonym* sub-feature (FR-027) beyond what the existing `scope` field already provides — the encryption-at-rest Security-MUST is this story's load-bearing deliverable; stable-session-pseudonym ergonomics can be a thin follow-up that simply uses `scope` as the session key (noted so a cold picker knows the sprint-plan row bundles both, but the MUST is encryption-at-rest).
- **Residual leak documented:** the blind-index reveals equality of `(scope, token)` pairs (needed for `O(1)` lookup). This is equality over **derived pseudonyms**, not PII, and is consistent with FR-019's deterministic surrogates. Record it in the module docstring + Evidence as a conscious trade-off; an alternate (decrypt-and-scan, no index) is noted as a switch-point for deployments that reject any equality leak.
